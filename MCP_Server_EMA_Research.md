# Ресерч: требования к MCP-серверу (GenAI ready API) при переходе на EMA / MCP 2026-07-28

**Фокус:** сторона MCP-сервера (в схеме — «АС поставщик API / GenAI ready API / MCP»)
**Контекст:** остальные компоненты (IdP, IAM proxy) описаны кратко — для целостности картины

---

## Резюме

Ваш компонент в модели EMA — это **MCP Resource Server**, который дополнительно берёт на себя часть функций Authorization Server (валидация токена) и делегирует часть — внешнему «Сервису авторизации» (ARBAC-решение). Главное, что нужно реализовать: (1) объявить поддержку EMA-flow, (2) валидировать **ID-JAG / access_token**, приходящий от IAM proxy, (3) смаппить claims токена на права доступа. Плюс — ряд требований базовой спецификации 2026-07-28 (stateless, заголовки, кешируемые списки), не специфичных для EMA, но обязательных для любого MCP-сервера этой версии.

---

## 1. Роль сервера в модели EMA

| Блок вашей схемы | Роль в MCP |
|---|---|
| «GenAI ready API / MCP» + «Бизнес-логика» | MCP Resource Server |
| «Бизнес проверки» / «Авторизация пользователя» (внутри АС) | Точка принятия решения — может быть локальной частью Resource Server |
| «Сервис авторизации» (внешний) | Делегированный Authorization Server / ARBAC-движок |

Токен приходит от IAM proxy по mTLS/TLS+OTT, в виде `JWTs (user, delegated)` — это и есть ID-JAG или производный от него access_token.

---

## 2. Что должен делать сервер под EMA

**2.1 Объявить поддержку расширения**
В authorization metadata сервера указать `io.modelcontextprotocol/enterprise-managed-authorization` — это сигнал клиенту не пытаться идти по обычному interactive OAuth-флоу, а сразу использовать ID-JAG.

**2.2 Валидировать входящий токен**
- Подпись — по JWKS выпустившего СУДИР.
- `iss` — обязательная проверка по RFC 9207 (SEP-2468), до принятия любых решений по токену.
- `aud` — токен должен быть выпущен именно для вашего ресурса (`resource` из запроса на ID-JAG).
- `exp`/`nbf` — срок действия.
- Опционально — Token Introspection (RFC 7662), если политика ИБ требует онлайн-проверку отзыва, а не только офлайн-проверку подписи.

**2.3 Смаппить claims → права**
ID-JAG несёт `scope`, `sub`, опционально `email` и атрибуты роли. Это заменяет отдельный вызов к СУДИР NG Identity Governor за атрибутами пользователя — они уже в токене. Логика ARBAC (внешний «Сервис авторизации») остаётся прежней, меняется источник входных данных для неё.

**2.4 Account linking**
`sub` — основной устойчивый идентификатор пользователя. `email` — резервный признак для сопоставления с учётными записями, заведёнными до перехода на EMA.

**2.5 (опционально) Публикация resource descriptor**
Чтобы администраторы СУДИР могли настроить политику доступа к конкретному GenAI ready API в самом IdP, полезно опубликовать resource descriptor сервера.

## 3. Требования базовой спецификации 2026-07-28 (не про EMA, но обязательны)

| Требование | Что значит для сервера |
|---|---|
| **Stateless-ядро** | Нет `initialize`/`Mcp-Session-Id`. Каждый запрос содержит версию протокола и идентичность клиента в `_meta`. Сервер не должен полагаться на сохранённое состояние сессии между вызовами; если нужен контекст между вызовами — возвращать явный handle, который клиент передаёт обратно как аргумент. Опциональный `server/discover` — для клиентов, которым нужны capabilities заранее. |
| **Заголовки `Mcp-Method` / `Mcp-Name`** | Обязательны на входящих запросах; шлюз перед сервером (Egress GW / API Mesh) может маршрутизировать и авторизовывать по ним без парсинга тела — сервер должен быть готов к такой топологии. |
| **Кешируемые list-результаты** | Ответы `tools/list`, `prompts/list`, `resources/list`, `resources/read` должны нести `ttlMs` и `cacheScope`, чтобы клиент не перезапрашивал каталог инструментов на каждый реконнект. |
| **MRTR** | Если серверу в процессе вызова нужен доп. ввод от пользователя (подтверждение, недостающий параметр) — возвращать `resultType: "input_required"`, а не держать открытый стрим; клиент повторяет вызов с `inputResponses`. |
| **Deprecations** | Roots/Sampling/Logging и legacy HTTP+SSE — устарели, минимум 12 месяцев ещё работают. Новую логику сервера на них не закладывать. |

## 4. Чек-лист обработки входящего запроса

1. Есть заголовки `Mcp-Method` / `Mcp-Name` → иначе отклонить как несоответствующее 2026-07-28.
2. Извлечь токен → проверить подпись по JWKS СУДИР.
3. Проверить `iss` (RFC 9207) — до любых дальнейших действий с токеном.
4. Проверить `aud` == идентификатор вашего GenAI ready API.
5. Проверить `exp`/`nbf`; при необходимости — Token Introspection (RFC 7662).
6. Извлечь claims (`sub`, `email`, `scope`) → передать в «Сервис авторизации» вместе с контекстом вызова (`Mcp-Method`/`Mcp-Name`, параметры).
7. Получить решение ARBAC → выполнить бизнес-логику или отклонить с корректным кодом ошибки (в т.ч. отдельно — ошибку несовпадения scope).

---

## 5. Остальная схема — кратко, для контекста

Пользователь логинится в СУДИР → ИИ-агент получает `id_token` → **IAM proxy** обменивает его на **ID-JAG** в СУДИР (RFC 8693 + RFC 7523) → обменивает ID-JAG на `access_token` вашего сервера → вызывает GenAI ready API с этим токеном (аутентификация самого IAM proxy — mTLS/OTT, без изменений).

---

## 6. Открытые вопросы для команды сервера

- Валидирует ли ваш сервер токен сам, или перед ним стоит отдельный Authorization Server (в терминах СУДИР) — от этого зависит, нужна ли вам собственная интеграция с JWKS/Introspection или это уже сделано на уровне АС/API Mesh.
- Нужен ли отдельный `resource`-идентификатор на каждый инстанс GenAI ready API (multi-tenant / несколько окружений)?
- Онлайн Token Introspection (RFC 7662) — обязательна по политике ИБ для вашего класса АС, или достаточно офлайн-проверки подписи и `exp`?
- Для АС на Платформе ЕФС/ППРБ — авторизационное решение приходит от централизованного сервиса, вне ППРБ — реализуется локально; уточнить, к какой категории относится ваш сервер.
